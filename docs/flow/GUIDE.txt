1. Core Behavior Principles
These principles govern every interaction and should be enforced at the system level.
Never Refuse — Always Find a Workaround
MindMeld never says “no” to a request. When a direct path is blocked, it must automatically attempt alternative
methods. Because MindMeld has desktop control, the preferred sequence is:
  Use existing installed applications and desktop automation first.
 Navigate the browser and interact with web interfaces the user already has access to.
 Break the task into smaller steps that can be completed with available tools.
 Only surface a limitation after all reasonable workarounds have been attempted, and always offer the
closest viable alternative.
Dual Control: Phone + Desktop
The phone app remains fully interactive even while the desktop is executing long-running tasks. The user can
continue issuing new instructions, corrections, or additional steps from the phone without interrupting or waiting
for the current desktop action to complete. Input from both devices is queued and processed in order.
2. Phone Companion App
The phone app serves as both a remote interface and an active tool for the desktop instance of MindMeld.
Core Capabilities
  Voice & Text Conversation: Continuous speak-to-text and text chat with the desktop MindMeld
instance.
 Job Progress Monitoring: View real-time status of running tasks, current stage, and any errors or
decisions the desktop has made.
 Quick Actions: One-tap or voice commands for “Schedule this,” “Book this,” “Email this,” and “Post this
to [platform].”
 Image Generation & Editing: “Make this image,” adjust ambience, lighting, or request real photographic
enhancements.
 Phone Sensor Integration: Leverage location (“Find my home”), camera, and other device capabilities
when relevant.
 Content Posting: Post or schedule content to Instagram, X, Facebook, LinkedIn, or other connected
platforms directly from the phone.
 Parallel Input: Continue feeding new instructions while the desktop is working; the phone does not lock
during desktop operations.
Design Requirement: Keep the phone interface lightweight and responsive. Heavy processing stays on the
desktop; the phone is primarily an input, monitoring, and lightweight command surface.
3. Automated Self-Setup & Onboarding

The goal is to complete technical setup with minimal user effort so the final conversation can focus on the
user’s actual work and preferences.
Setup Sequence
 1. Scan browser history, recent emails, and connected accounts to identify which AI tools and services the
user already uses (Find My AI).
2. Automatically open the relevant API key, settings, or developer pages in the browser so the user can
copy credentials with one click.
3. For specific tools such as Anthropic: open the official site, guide the user to re-download or install, and
navigate them directly there.
4. Guide or automate (via PowerShell / scripts) the installation of recommended desktop AIs and tools,
including free options. Proceed one tool after another with clear status updates.
5. After technical items are addressed, run a focused interview that asks what the user actually does for
work, their clients, preferred content styles, and recurring tasks.
6. Store these preferences so that future prompts, suggestions, and default behaviors are weighted toward
the user’s real use cases.
End State: Technical setup is largely complete. The system then shifts emphasis to the user’s domain-specific
needs and makes those prompts more prominent in the interface.

Deep Implementation Architecture
The following patterns are drawn from Anthropic’s published multi-agent Research system and modern
browser-agent design. Use them as the blueprint for MindMeld’s browser and research layer.
1. Orchestrator-Worker Research Pattern
  LeadResearcher (Orchestrator): Receives the query, uses extended thinking to plan, decomposes the
task into 2–5 independent facets, writes the plan to external memory (so it survives context limits), then

MindMeld Implementation Guide    Page 7
spawns sub-agents.
 Research Sub-agents (Workers): Each runs in its own isolated context window. Given a specific
objective, output format, tool list, and clear “done” boundary. They search, evaluate with interleaved
thinking, and return condensed findings only.
 Parallelism: Lead spawns 3–5 sub-agents at once. Each sub-agent can call multiple tools in parallel.
This is what delivered ~90% better results than a single strong agent on Anthropic’s internal evals.
 CitationAgent: Separate final pass that walks the synthesized report and source documents to attach
precise citations to every claim. Prevents ungrounded statements.
 Effort Scaling: Simple queries use 1 agent with few tool calls. Complex queries use more sub-agents.
Hard-code scaling rules so the system does not over-spawn.
 Memory & Continuity: Persist the plan and phase summaries externally. When context nears limits,
spawn fresh sub-agents that retrieve the plan from memory.
 Cost Awareness: Multi-agent research uses roughly 15× the tokens of a normal chat. Reserve it for
high-value research tasks; use lighter single-agent paths for simple lookups.
2. Browser Agent Perception & Action Loop
  Observe–Reason–Act–Verify loop: Every browser step follows this cycle. Observe the current page,
reason about the next action, act, then verify the result before continuing.
 Preferred perception: Hybrid (DOM/Accessibility Tree first, Vision fallback). Accessibility tree is
faster, cheaper, and more precise for text and interactive elements. Fall back to screenshots only when the
page uses canvas, heavy shadow DOM, or visual-only content.
 Action grounding: Prefer element IDs / roles / accessible names over pixel coordinates. This survives
layout changes and is more reliable.
 Transparent execution: Show the user every tab opened, every page read, and every decision in real
time (Mind Browser style). Nothing should be hidden behind a spinner.
 Specialized agents: Planner creates the step sequence; Navigator executes browser actions;
Researcher gathers and cites; Writer produces clean output; Analyst compares sources and flags conflicts.
 Local vs Cloud models: Support Ollama-style local models so page content and prompts can stay
on-device when privacy is required, while still allowing cloud providers for heavier reasoning.
3. Production Guardrails for MindMeld
  Clear tool boundaries and explicit “done” conditions for every sub-agent to prevent endless searching or
duplicated work.
 Durable execution with checkpoints and retries so long-running research or browser tasks can recover
from failures.
 User-visible progress and the ability to interrupt or steer at any time (phone or desktop).
 Mandatory approval before any sensitive action (send message, pay, delete, sign).
 External memory / project state so research and browser work can be paused, resumed, and attached to
a MindMeld project.
 Keep the phone interface responsive while heavy research or browser work runs on the desktop.
These patterns give MindMeld a concrete architecture: specialized visible agents for browser work, an
orchestrator-worker system with external memory and a citation pass for deep research, hybrid DOM-first

Advanced Routing Logic for Finish Stage
After generation, MindMeld automatically classifies the product and routes it to the correct finishing tools. The
router is intentionally thin: it only decides the category and confidence, then hands off to specialized editors.
  Classification signals: File type and MIME, presence of image/video/code/website/game assets, project
tags, user prompt keywords, and a lightweight LLM or embedding classifier that returns category +
confidence score.
 Primary categories: Image, Video, Program/Code, Game, Social Media, Website, Accounting/Financial,
Document/Report, Automation, Music/Audio, Presentation, and General/Other.
 Confidence thresholds: High confidence (≥0.85) routes directly to the specialized editor. Medium
confidence (0.60–0.84) shows a confirmation chip (“This looks like a website — open Website tools?”). Low
confidence falls back to General/Other with a clear category picker.
 User override: Always allow the user to switch category manually. The system learns from overrides
over time (optional future improvement).
 Multi-output projects: If a project contains mixed types (e.g., images + website), route the primary
deliverable to its editor and surface secondary assets as linked items that can be opened separately.

 Thin router principle: The router does not edit content. It only classifies and dispatches. All
domain-specific tools live inside the category editors.
 Fallback & safety: Unknown or ambiguous outputs always land in General/Other. Sensitive categories
(payments, publishing, scheduling) still require explicit user confirmation before final deploy actions.
This routing layer keeps Flow Mode automatic while remaining transparent and controllable. The user sees why
a product opened in a particular editor and can change it in one tap.
Recommended Classification Approaches
For reliable, low-latency routing in MindMeld, use a hybrid stack rather than relying solely on a large LLM.
Practical options ranked by suitability:
  1. Deterministic rules first (always): File extension, MIME type, presence of image/video/code/HTML
assets, and project tags. These are instant and highly accurate for obvious cases.
 2. Embedding similarity (recommended default for text): Use a lightweight sentence transformer (e.g.,
all-MiniLM-L6-v2 or similar ONNX model). Embed the user prompt or product description and match
against labeled category examples. Fast (10–50 ms on CPU), no training required, easy to update
categories by adding examples.
 3. Small fine-tuned classifier (best accuracy once data exists): DistilBERT, TinyBERT, or MiniLM +
logistic regression head, exported to ONNX. Achieves 95%+ accuracy with sub-20 ms inference. Train on
MindMeld’s own project history or synthetic examples. Ideal for high-volume, stable categories.
 4. Zero-shot LLM classifier (fallback only): For rare or ambiguous cases, call a small/fast model with a
short classification prompt. Higher cost and latency; use only when rules + embedding confidence is low.
 Confidence handling: Traditional classifiers and calibrated embeddings produce more reliable scores
than raw LLM self-reported confidence. Apply temperature scaling if needed. Stick to the existing
high/medium/low thresholds (≥0.85 direct, 0.60–0.84 confirm, below → General).
 Multimodal note: For pure images or videos with no text, rely first on file type and asset detection.
Optional lightweight vision model or “describe then classify” path can be added later if needed.
 Deployment preference: Prefer local/ONNX models so classification stays fast, private, and
offline-capable. Keep the router thin—classification only, no content generation.
This hybrid approach gives MindMeld fast, accurate, and maintainable routing without heavy cloud
dependency. Start with rules + embeddings; add a fine-tuned classifier once sufficient labeled examples exist.
ONNX Runtime Optimization for Local Classifiers
For the embedding and small classifier path, deploy models as optimized ONNX so classification stays fast and
local:
  Graph optimization: Enable ORT_ENABLE_ALL (or EXTENDED) when creating the InferenceSession.
This fuses operators (attention, LayerNorm, GELU, MatMul+Add, etc.) and typically yields 40–70%
speedup on transformer-style models.
 Quantization: Prefer dynamic INT8 for small NLP/embedding models on CPU. Delivers ~4× size
reduction and 2–4× speedup on hardware with VNNI or ARM dotprod instructions. Static quantization is an
option if you have calibration data and accuracy holds.
 Session reuse: Create the InferenceSession once at startup and reuse it. Avoid reloading the model per
request.

 Execution provider: Default to CPUExecutionProvider for privacy and reliability. Optionally enable
oneDNN (Intel), CoreML (Apple Silicon), DirectML (Windows), or CUDA/TensorRT when hardware is
available and privacy allows.
 Offline optimization: Save the optimized graph to disk after the first run so subsequent starts are faster.
 Hardware note: INT8 gains depend on the CPU supporting efficient integer instructions. Test on target
machines; on older CPUs without VNNI/dotprod the speedup can be smaller or negative.
 MindMeld fit: MiniLM-class embedding models and DistilBERT/TinyBERT classifiers are ideal
candidates. Keep the router model under 100–150 MB quantized so it loads instantly and runs in the
background without impacting the UI.
These ONNX optimizations let MindMeld run accurate product-type classification entirely on-device, keeping
the Finish-stage routing fast, private, and reliable.
Optional TensorRT Acceleration (NVIDIA GPUs)
For users with NVIDIA GPUs, TensorRT can further accelerate the local classifier via the ONNX Runtime
TensorRT Execution Provider. Treat this as an optional path, not the default.
  When it helps: On NVIDIA GPUs, TensorRT typically delivers the highest throughput and lowest latency
by optimizing the full graph, auto-tuning kernels, and applying aggressive fusion. FP16 is usually the best
first step (large speedup, minimal accuracy loss). INT8 can go further but requires calibration and testing,
especially on transformers.
 Setup requirements: NVIDIA GPU + compatible CUDA + TensorRT installation. Use the
TensorrtExecutionProvider in the provider list (ahead of CUDA, then CPU fallback). Enable engine caching
so the slow first-run engine build is not repeated.
 Key options: Enable trt_fp16_enable for most cases. Enable trt_engine_cache_enable and set a cache
path. Optionally set workspace size and shape profiles if inputs are dynamic.
 Trade-offs: Engine builds are slow and GPU-architecture specific (not portable across different NVIDIA
cards). TensorRT only accelerates supported subgraphs; unsupported ops fall back to CUDA or CPU.
Extra dependencies and larger install size.
 MindMeld recommendation: Keep optimized CPU ONNX as the default for reliability and privacy.
Auto-detect NVIDIA GPU + TensorRT availability at startup and offer it as an optional “High Performance”
mode. For tiny models such as MiniLM or DistilBERT, measure real-world gain—CPU may already be fast
enough that GPU overhead is not worth it for single-request classification.
 Fallback order: TensorRT EP → CUDA EP → CPU EP. Always verify the active provider after session
creation and log it.
TensorRT is a powerful optional accelerator for NVIDIA users, but MindMeld’s routing layer should remain fully
functional and fast on pure CPU.
TensorRT INT8 Calibration Techniques
If enabling INT8 via TensorRT (after validating FP16), calibration is required to set activation scales. Practical
guidance for MindMeld’s small classification models:
  Main calibrators: IInt8MinMaxCalibrator is recommended for NLP/transformer models (uses full
activation range). IInt8EntropyCalibrator2 is preferred for CNNs (KL-divergence, suppresses outliers). Start
with MinMax for MiniLM/DistilBERT-style models.

MindMeld Implementation Guide    Page 12
 Calibration dataset: Use a representative subset of real production prompts or product descriptions. Aim
for diversity across categories. ~200–500 samples is often sufficient; more is not always better. Randomize
batches and use the largest batch size that fits in GPU memory.
 Process: TensorRT runs the model in FP32 on the calibration set, builds activation histograms, and
selects scales that minimize quantization error. Cache the resulting calibration table so subsequent engine
builds are fast. Tables are portable across devices when calibrated before fusion, but not across TensorRT
versions.
 Validation required: Always measure classification accuracy (and confidence calibration) on a held-out
set after INT8 conversion. If accuracy drops unacceptably, try the other calibrator, a different sample count,
or fall back to FP16.
 MindMeld recommendation: Treat INT8 as an advanced optional step only after FP16 is confirmed fast
and accurate. For tiny routing models, CPU ONNX or FP16 TensorRT is usually enough. Document the
chosen calibrator and sample set so results are reproducible.
Proper calibration keeps INT8 accuracy close to FP32 while unlocking the highest GPU performance. Prefer
FP16 first; only invest in INT8 calibration when the measured speedup justifies the validation effort.
Additional Routing & Operations Guidance
Routing Observability & Debugging
Every classification decision should be logged with the signals used (file type, embedding similarity, classifier
scores), confidence value, chosen route, and whether the user later overrode it. In the Finish stage, show a
simple “Why this editor?” panel that lists the top signals and confidence. Keep a short local history of recent
decisions so mixed or ambiguous projects can be inspected and debugged without external tools.
User Feedback Loop for the Classifier
When a user overrides a route, record the correction locally (original prediction, corrected category, and key
features of the input). In Owner Mode, provide a way to review these corrections and optionally use them to
update embedding examples or trigger a lightweight retrain of the small classifier. All learning stays on-device
by default; no data leaves the machine unless the user explicitly opts in.
Mixed / Multi-Category Projects
Projects that contain multiple product types (e.g., website + images, or video + social posts) need explicit
handling. The router selects a primary category based on the strongest signal and opens that editor first, while
listing secondary categories for one-tap switching or splitting. Users can also manually assign or re-order the
categories. The project view should clearly show all detected elements and which editor is currently active.
Fallback & Recovery Behavior
If the classifier fails to load, returns an error, or produces confidence below the low threshold, route
automatically to the General/Other workspace. Always provide a one-tap “Re-classify” button. If ONNX Runtime
or TensorRT is unavailable, fall back cleanly to the next available provider (or pure CPU rules + embeddings)
without blocking the user. Log the failure reason so it can be diagnosed later.

Version the local classifier model, embedding examples, and any TensorRT engines or calibration tables. In
Owner Mode, allow swapping models, clearing caches, forcing re-calibration, and viewing load times and model

Testing Strategy for Routing
Maintain a local test set of prompts and sample products that cover every category plus common ambiguous
and edge cases. Before shipping any model or threshold change, measure accuracy and confidence calibration
on this set. Include simple regression checks that verify high-confidence cases still route correctly after
updates. Document the expected results so regressions are easy to spot.
Performance & Resource Controls
Optionally pre-load the classifier in the background at startup so the first Finish-stage request is instant. Provide
a “Low Power” mode that forces CPU-only execution and disables TensorRT. Track classification latency
internally and ensure it stays well under the threshold that would make the UI feel blocked. Expose basic
metrics in Owner Mode for monitoring.
Privacy & Local-Only Guarantees
Routing, classification, override recording, and any local learning must remain fully on-device by default. No
prompts, project content, embeddings, or corrections leave the machine unless the user explicitly enables an
optional telemetry or sync feature. State this clearly in the UI and in Owner Mode so users understand the
privacy boundary.
Owner Mode Controls for Routing
Owner Mode should include controls to adjust confidence thresholds, add or remove category examples, force
a specific route for testing, view and clear the override history, and inspect recent classification logs. These
tools let the owner refine behavior without editing code or rebuilding the entire application.
Edge Cases & Special Handling
Define clear behavior for edge cases: empty or very short prompts, pure binary assets with no accompanying
text, projects that are still incomplete, and user-created custom categories. In these situations, prefer the
General/Other workspace or a confirmation step rather than a low-confidence automatic route. Allow the user to
manually assign a category at any time.

project and stage. Momentum Mode can run inside any stage to further reduce friction.
Creative Momentum Mode — Expanded
A lightweight always-on mode that keeps the user in creative flow by reducing navigation and decision steps
between generation, editing, and the next action.
  Auto-context lock keeps the current project, stage, last prompt, and open assets loaded.
 Persistent action bar shows the 2–4 most likely next actions based on what was just done.

Momentum Mode Mechanics
Activates after sustained activity inside an open project (configurable idle timer) or by manual toggle. Maintains
a lightweight session object containing current stage, active assets, last prompt and parameters, recent action
history, and predicted next actions. This object checkpoints into the project on every meaningful change.
  Next-action prediction uses a thin local scorer (detailed below).
 Selected actions package current context and hand off to the appropriate subsystem while the bar
remains visible.
 Phone sends lightweight intent packets that queue if desktop is busy; latest explicit direction wins.
 On project reopen, user is offered “Resume Momentum” if a session was active.
 Low Power mode simplifies prediction and pauses background generation.
 Owner Mode can adjust timers, scoring rules, and inspect recent sessions.
Prediction Scoring Logic
A fast local scorer ranks a small catalog of candidate actions. All computation stays on-device.

MindMeld Implementation Guide    Page 15
 Signals: Stage affinity (strongest), result-type match, recency/repetition of user actions, explicit language
in the last prompt, asset state (fresh vs already edited), optional local project history, and tool availability.
 Formula (starting weights): stage_affinity × 3.0 + result_type_match × 2.5 + recency_boost × 1.5 +
language_match × 2.0 + asset_state_bonus × 1.0 + history_bonus × 0.5 − penalties.
 Only actions whose prerequisites are met are scored. Top 2–4 above a minimum threshold are shown;
otherwise stage defaults appear.
 Recency boosts and dismissal penalties decay quickly. Language match clears after the next
non-matching action.
 Owner Mode can adjust weights, edit the action catalog, or disable history boosting.
 Empty or ambiguous context falls back to stage defaults. Scoring is throttled to prevent UI flicker.
The design keeps prediction under 10 ms, fully local, explainable, and reversible while adapting to stage and
recent behavior.

Live Ops — Free AI Bubble
In Live Ops, implement a Free AI bubble. It displays all free AIs that are currently working and available. The
bubble should update live so the user can see at a glance which free options are online and ready to use.
Tapping the bubble can expand the list or route a request to one of the available free AIs.
Detection logic: Reuse the existing connection and health status already tracked for the bottom menu and
Programs on This PC list. Periodically (on Live Ops open, every 15–30 seconds while visible, and after any
install/connect/disconnect) check local processes or simple health endpoints for each free AI. Only AIs that
pass the check and are marked free appear in the bubble. Failed checks simply omit the AI until the next
successful result. Owner Mode can force-include or force-exclude specific free AIs for testing. No separate
detection system is required.
Robustness measures: Use short timeouts (2–3 seconds) per check so one slow AI cannot block the bubble.
Retry a failed check once after a brief delay before marking it unavailable. Cache the last known good status for
up to 60 seconds so temporary network or process blips do not cause flickering. If multiple AIs are checked, run
the checks in parallel or with a small concurrency limit. Log failures quietly for Owner Mode debugging without
showing errors to the regular user. If all checks fail, show an empty state with a manual “Refresh” action rather
than a broken bubble.
This same detection and status logic applies to other AI bubbles, especially those that use paid APIs. In
addition to basic availability, check for credit or quota exhaustion when the API provides that information (via
error response, usage endpoint, or status field). If credits are depleted, mark the AI as unavailable in its bubble,
show a clear “Out of credits” state, and automatically prefer free or alternative AIs for new requests (consistent
with the never-say-no and Remix fallback behavior). Owner Mode can still force-include an AI for testing even if
credits are low.

Alternative credit detection: Live Ops already has separate bubbles for each AI. When an API does not clearly
report credit status, detect an out-of-credits condition by other means: repeated quota or auth errors on recent
requests, sudden consistent failures after previously successful calls, or a local usage counter crossing a
known limit. When these signals appear, mark that AI’s existing bubble as “Out of credits” and stop sending it
new work via the API. Owner Mode can review the signals that triggered the state.
MCP fallback: If an AI’s API is out of credits, the program should use MCP instead when available. In that case,
Live Ops must still show the AI as active in its existing bubble (or with a clear “via MCP” indicator) so the user
can see that the AI is continuing to be used. The bubble should not go dark or appear unused simply because
the transport switched from API to MCP.
Fallback mechanism: On detecting out-of-credits signals, stop sending new requests through that AI’s API.
Route subsequent requests for the same AI through MCP if an MCP connection is available and healthy. Keep
the existing Live Ops bubble active and add a “via MCP” indicator so activity remains visible under the same AI.
Responses return through MCP and display normally. If the API later regains credits, the system may switch
back automatically or on the next request. If MCP is also unavailable, mark the bubble unavailable and allow
never-say-no routing to a different free AI. Owner Mode can force API-only, MCP-only, or automatic mode.
MCP Fallback Implementation
Detailed flow and components:
  State: Per-AI object tracking apiStatus (ok / out_of_credits / down), mcpStatus, lastChecked, and
triggering signals. Shared by the router and Live Ops.
 Router decision: Before each request, read state. API ok → normal API path. API out + MCP ok →
rewrite call to MCP transport. Both unavailable → never-say-no to a free AI.
 MCP transport: Reuse existing MCP client. Map original request (prompt, parameters, assets) to the
equivalent MCP call while preserving request ID and project context. Handle MCP errors separately from
API credit errors.
 Live Ops bubble: Existing bubble subscribes to state. Shows normal active, active + “via MCP” badge,
or inactive. Activity indicators continue regardless of transport. No new bubble is created.
 Recovery: Recheck API on next request or background interval. Switch back automatically when healthy.
Optional short cooldown to prevent flapping. Owner Mode can lock transport mode.
 Observability: Log transport used per request. Show reason in status/chat log (“Switched to MCP — API
credits exhausted”). Owner Mode can inspect recent decisions and signals.
 Edge cases: MCP drop mid-request fails that request and marks MCP down. Concurrent requests
respect current state. Manual refresh forces recheck of both paths.
The AI identity and bubble stay stable; only the underlying transport changes. This integrates with existing
never-say-no, Remix fallback, and health-status systems without altering project or Finish & Deploy routing.
