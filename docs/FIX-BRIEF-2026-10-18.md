### (e) Local server: block cross-site requests
Problem: local mode (`server/index.js`) binds 127.0.0.1 with no auth. `readBody` parses any body as JSON whatever its content type. CORS isn't sent locally, but "simple" cross-site requests (text/plain POST) still run. So any website the customer visits could likely start chats, councils or missions on their keys (`/api/chat`, `/api/council`, `/api/mission`), replace their keys (`/api/keys`) or change settings. DNS rebinding could also read `/api/state`. This was found by reading the code, not tested.

Do:
1. **Per-launch token:** at startup generate a random 32-byte token (in memory, new on every launch). Inject it into `index.html` when serving it (for example a `<meta name="cc-token">` tag); `web/app.js` sends it as an `X-CC-Token` header on every `/api` call and as the first WebSocket message (the hosted WebSocket already uses a first-message auth pattern). Require it on every `/api/*` route except `/api/health` and `/api/config`, and on `/ws`. Downloads such as `/api/setup/bookmarks.html` should be fetched with the header and saved as a blob, not opened as a plain link.
2. **Host check:** in local mode, reject requests whose `Host` isn't `127.0.0.1:<port>` or `localhost:<port>` (blocks DNS rebinding). Return 421 or 403.
3. **Origin check:** if an `Origin` header is present, it must be `http://127.0.0.1:<port>` or `http://localhost:<port>`; otherwise 403. Same for the WebSocket upgrade.
4. **Content type:** POST, PUT and DELETE with a body must have `content-type: application/json`, otherwise 415. Apply this in hosted mode too.
5. Keep Electron working (it loads `http://127.0.0.1:<port>/`), plus the `Start Command Center.cmd` browser flow, the Claude preview pane (`.claude/launch.json`) and phone pairing in hosted mode. The demo provider server in `server/mock.js` already binds 127.0.0.1; leave it but make sure it can't spend anything real.
6. Hosted mode keeps bearer-token auth as it is.
